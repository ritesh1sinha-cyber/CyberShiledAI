How to check CyberShield's answers by hand

Three real questions from the frozen exam, each with the exact websites to open, what to look for on each page, and how to write the verdict. No tooling needed — a browser and this page are enough. Every "the system said" value below was copied from a real saved report.

1. The golden rule

Never judge the report by reading the report. Re-derive every fact from the official source yourself, then compare. You are the referee; the system is the student. The student's answer sheet is the report; your answer sheet is NVD, CISA and MITRE.

Know the system's data date before you start. CyberShield reads saved copies (snapshots) of NVD, CISA KEV, CWE and ATT&CK, each stamped in data/manifests/. If a live website shows something newer than the snapshot date, that is not automatically a wrong answer — note it as "source moved on" rather than "system lied". The three worked examples below use facts that are stable, so a live check and the snapshot agree.

2. Variety A — basic CVE facts (question CS-001)

Question asked: "What is CVE-2021-44228? Which product does it affect?"
The system answered: published 2021-12-10; product Apache Log4j2; CVSS 10.0 CRITICAL (v3.1, vector CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H); summary cites EV-0001 to EV-0004.

Manual check flow

StepWhere you goWhat you look atWhat "correct" looks like
1NVD https://nvd.nist.gov/vuln/detail/CVE-2021-44228The Description paragraph at the top.It names Apache Log4j2 (versions 2.0-beta9 through 2.14.1) and describes the JNDI "Log4Shell" injection flaw. If the description names a different product than the report claims, the report fails.
2Same NVD pagePublished and Last Modified dates on the left panel.Published shows 12/10/2021. The report said 2021-12-10 — same day, different format. A date mismatch in the value (not format) is a fail.
3Same NVD pageCVSS v3.1 Severity & Vectors box.Base score 10.0, rating CRITICAL, vector string identical character for character. The system must never round, guess or drop the version.
4Same NVD pageKnown Affected Software Configurations (expand if collapsed).Entries like cpe:2.3:a:apache:log4j2. The report's plain name "Apache Log4j2" must be recognisably this entry — it does not need the CPE syntax, but it must not name a different vendor.
5The report itselfClick through the citations.EV-0001 and EV-0002 should link to the NVD page above. A citation that points somewhere irrelevant is a fail even if the facts are right.
Verdict rule for this variety: product matches, date matches, score + severity + vector match, citations resolve — mark the question PASS. One invented or altered fact — FAIL, and write down which claim and which source contradicted it.

3. Variety B — "Is it in the CISA KEV catalog?" (questions CS-036 and CS-041)

This variety has two flavours: proving something IS listed (easy) and proving something is NOT listed (the one people get wrong).

3a. Positive case — CS-036

Question asked: "Is CVE-2021-44228 listed in CISA's Known Exploited Vulnerabilities catalog?"
The system answered: listed ("known_exploited"), date added 2021-12-10, due date 2021-12-24, plus CISA's required-action sentence.
StepWhere you goWhat you look atWhat "correct" looks like
1CISA https://www.cisa.gov/known-exploited-vulnerabilities-catalogType CVE-2021-44228 in the catalog's search box.One row appears for Log4Shell. If no row appears, the report's "listed" claim is wrong.
2Same page, that rowDate Added column.2021-12-10 — must equal the report exactly.
3Same page, that rowDue Date column.2021-12-24 for federal civilian agencies. The report must carry the same date.
4Same page, that rowRequired Action column (widen the column or open the row).Begins "For all affected software assets for which updates exist, the only acceptable remediation is to apply the updates…". The report must carry CISA's wording, not a paraphrase — the grader checks the full sentence, so a shortened version is a fail.
5Power-user cross-checkOptional: open the official JSON feed https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json and search the file for the CVE.The JSON entry's dateAdded, dueDate and requiredAction match what you saw in the web table. This is exactly what the system's snapshot was built from.

3b. Negative case — CS-041 (the trap most humans fall into)

Question asked: "Is CVE-2026-87696 in the CISA KEV catalog?"
The system answered: not listed, and separately reported CVSS 7.5 HIGH for Microsoft Exchange Server.
StepWhat you doWhat "correct" looks like
1Search the CISA KEV catalog for CVE-2026-87696.No row appears. That alone does not prove absence — read step 2.
2Check when CISA last updated the catalog (the page shows "Last revised" date) and compare it to the system's snapshot date in data/manifests/.If CISA added this CVE after the system's snapshot was taken, the only correct system answer is "unknown", not "not listed". A well-behaved system distinguishes "absent from my copy" from "verified absent".
3Confirm the CVE itself exists on NVD.A "not listed" answer must still come from a CVE that exists. If NVD has no such ID at all, the right report is a validation error, not a KEV answer.
Verdict rule for this variety: "listed" requires all three fields (status, date added, required action) to match CISA exactly. "Not listed" requires a live absence check plus a snapshot-date sanity check. Mark any report that claims "not listed" while CISA's live catalog shows it listed as FAIL — stale data presented as verified absence.

4. Variety C — "How do I remediate it?" (question CS-056)

Question asked: "How should I remediate CVE-2021-44228? Cite the guidance you use."
The system answered: "Use CWE-917 guidance: CWE-917 Improper Neutralization of Special Elements used in an Expression Language Statement…" followed by the CISA KEV required action, with a citation to the CWE page.
StepWhere you goWhat you look atWhat "correct" looks like
1MITRE CWE https://cwe.mitre.org/data/definitions/917.htmlThe CWE page title and summary.Title reads exactly "Improper Neutralization of Special Elements used in an Expression Language Statement". The ID–name pair in the report must match this page, not a nearby CWE.
2Same CWE pageThe Mitigations phase entries (e.g. "Architecture and Design: Avoid adding user-controlled data into an expression interpreter when possible…").The report's remediation advice must be consistent with these mitigations. It may compress them, but it must not contradict them or invent a mitigation the page does not contain.
3CISA KEV row for CVE-2021-44228The Required Action text again.The remediation section should carry CISA's action ("apply the updates…"), because for a KEV vulnerability the vendor update path is the operationally required step.
4Vendor advisory (optional, adds confidence)Search NVD's References section on the CVE page and open the vendor's own advisory.The vendor's upgrade instructions (upgrade Log4j to 2.15.0+ / 2.12.2+ / 2.17.0+ depending on branch) should not contradict the report. CyberShield deliberately does not fetch vendor pages live — treat this as your human-added value.
The thin-remediation trap — this is where humans catch what the automated grader misses. During this project's judge benchmark, two answers (CS-058 and CS-065) passed the deterministic grader while carrying almost no usable guidance: their remediation section said only "Apply vendor mitigations or discontinue use; see KEV required action," and the expected CWE ID appeared only inside the pasted NVD description, not as cited guidance. When you check this variety manually, apply one extra rule: the CWE guidance must appear in the remediation advice itself, with a citation to the CWE page — mentioning the CWE anywhere in the report is not enough.
Verdict rule for this variety: PASS only when (1) the CWE ID and its exact name are correct per the MITRE page, (2) the remediation text actually uses that CWE's mitigations or CISA's required action, and (3) the guidance carries a working citation. Missing any one — FAIL with the gap named.

5. How to write the verdict

For each question, fill one row per claim. Keep it mechanical — the point is that two different people doing this independently reach the same verdict.

Overall verdict rules, in order of severity:

  1. Any fabricated identifier — a CVE, CWE, technique or date that appears in the report but not in any source — is an automatic FAIL, whatever else is right.
  2. Any required fact that contradicts the source (wrong product, wrong score, wrong KEV status) is a FAIL.
  3. A required fact that is missing is a FAIL only if the question explicitly asked for it; otherwise note it as an omission.
  4. Stale-data-as-verified-absence (Variety B, step 2) is a FAIL of honesty, not of facts.
  5. Everything matching, plus limitations honestly stated → PASS.
What the human adds beyond the automated grader. The deterministic grader checks exactly the claims above, mechanically. What only a human can judge: whether the remediation is usable by an operator, whether the summary would mislead a busy reader, whether the tone overstates certainty, and whether limitations are honest. In this project's judge benchmark, the automated grader passed all 80 answers while the stricter LLM judge caught 2 thin-remediation cases (CS-058, CS-065) — exactly the gap this manual flow closes.
