# CyberShield AI — Scope (v1, frozen 2026-11-06)

Solo build, 4 weeks, 40 h/week. Python 3.11, CPU-only retrieval, hosted Qwen endpoint.
This document is the contract for everything after it. Changes require a dated entry in §8.

## 1. Purpose

Answer one question well: *given a CVE, what is its severity, is it exploited, what should be done, and what is the evidence?* The system is decision support. It never executes, exploits, or changes anything.

## 2. Supported requests

| Input | Behaviour |
|---|---|
| Exactly one CVE ID, bare or inside a sentence | Full investigation |
| Natural-language question containing exactly one CVE ID | Full investigation, requested sections honoured where supported |
| More than one CVE ID | Rejected with a validation error (`multiple_cves_unsupported`) |
| No CVE ID (product/version only, "am I affected?") | Rejected with `cve_required`. Version-range comparison is out of scope for v1 |
| Anything outside the vulnerability domain | Refused by the classifier |

Rationale: product/version matching needs CPE 2.3 range parsing and produces "cannot determine" for most real inputs. It is the highest-effort, lowest-demonstration-value component in the original proposal. Deferred, not forgotten.

## 3. Output contract

Eight sections, all optional content rendered as explicit unknowns rather than omitted silently:

1. `summary` — plain language, no new facts beyond `cve`, `kev`, `remediation`.
2. `cve` — description, CVSS, severity, published/last-modified.
3. `affected_products` — from NVD configurations; empty list when unavailable.
4. `kev` — status with catalog version and check time.
5. `attack_mapping` — curated mappings only (§6, D3).
6. `remediation` — retrieved guidance, each item carrying at least one evidence ID.
7. `risk` — deterministic tier plus drivers (§6, D8).
8. `limitations` — explicit unknowns, stale sources, failed lookups.

**Null semantics:** unknown is `null`, never `0`, `""` or `"N/A"`. CVSS `0.0` is a legitimate score and is distinguishable from unknown because `severity` must be `NONE` and `cvss_version` must be present when a score exists.

## 4. Non-goals and refusals

Never: exploitation instructions, exploit code, malware, credential theft, unauthorised access guidance, autonomous remediation, production changes, arbitrary tool or URL invocation.

Over-refusal is a defect: refusing a well-formed single-CVE question counts against task completion, so the refusal set is tested separately from the supported set.

## 5. Frozen decisions

**D1 — CVSS precedence.** Read `metrics` from the NVD 2.0 response and take the first available in order: `cvssMetricV31` → `cvssMetricV30` → `cvssMetricV2`. Prefer `type == "Primary"` within a set, else the first entry. Record `cvss_version`, `cvss_score`, `severity`, `cvss_vector`, and `cvss_source` (`nvd` when type is Primary, else `cna`). Never merge fields across metric sets. `ssvcV203` is not CVSS and is excluded. Measured for CVE-2021-44228: `cvssMetricV2` and `cvssMetricV31` present, no v3.0, no v4.0 — so absence of v3.1 must be an ordinary case, not an error.

**D2 — KEV semantics.** Three states: `known_exploited`, `not_listed`, `unknown`. `not_listed` is only valid when the feed was successfully loaded and its `catalogVersion` recorded. The original seven-day freshness rule was superseded for the demo by D13: dated snapshots at or before investigation time are accepted; undated or future-dated snapshots remain `unknown`.

**D3 — ATT&CK.** No official CVE→technique mapping exists, and the model must not invent one. Ship a curated table of verified mappings for the CVE set we evaluate; anything else returns `attack_mapping: []` with a limitation note. `basis` is `curated` or `source_reference` — there is no `model_guess` value in the schema, by construction.

**D4 — Step definition.** One step = one executed graph node. The executor node counts once regardless of how many tools run inside it in parallel. Every retry counts as a new step. Hard cap 10, enforced in the router and asserted by a test.

**D5 — Corpus.** NVD records are structured tool responses, not retrieval documents, to avoid double-counting the ≥500 gate and inflating recall. Retrieval corpus: ATT&CK Enterprise techniques (~190), OWASP cheat sheets (~121), NIST guidance (~30), CWE entries (~150). Target ≥500 unique valid documents after dedup; actual counts reported from the manifest.

**D6 — Latency.** Measured 92.9 tok/s median on the hosted endpoint. Target **P95 ≤ 20s**, not 15s; the original 15s assumes an unmeasured endpoint. The original ≤3-call/400-token budget was superseded by D13/D14: the endpoint allows up to 1,024 output tokens and 8,192 combined tokens; multi-agent requests use up to five sequential Qwen calls including one refined retrieval retry. KEV feed is loaded from the local snapshot, never fetched per request. Streaming is unusable (proxy buffers SSE), so the UI renders stage progress.

**D7 — Traceability.** Every material claim in `summary`, `remediation` and `risk` carries an evidence ID that resolves to an existing `Evidence` record for the same request. Enforced by `validate_citations()`, not by prompt wording.

**D8 — Risk tier.** Deterministic: `critical` if KEV-listed and CVSS ≥ 9.0; `high` if KEV-listed or CVSS ≥ 9.0; `medium` if CVSS ≥ 7.0; `low` if CVSS < 7.0; `unknown` if CVSS is null. Drivers list the facts used. The model may explain the tier, never choose it.

**D9 — Baseline prompts and grading.** P0 = plain assistant, prose. P1 = fixed JSON contract (eight sections, null when unknown), no evidence. P2 = P1 plus honesty/safety rules (no guessing, no claimed lookups, refuse unsafe or unanswerable requests). All three run with `temperature=0`, `max_tokens=400`, no tools or retrieval. Grading is rule-based (`app/grading.py`), never model-judged: exact facts must match the frozen values; the remediation rubric requires the CVE, a concrete action and a named guidance source; adversarial items are graded on behaviour, not wording. A question passes only when every check passes.

**D10 — Local runtime boundary (2026-11-11; updated by D14).** FastAPI exposes `POST /investigate`, `GET /health` and bounded newest-first `GET /history`; Streamlit calls that API rather than constructing the workflow or Qwen client directly. Both services bind to localhost only. The service creates the request/trace ID before workflow execution and serializes investigations so the one-active-Qwen-request rule holds across web requests. Invalid input returns HTTP 422 with the §2 codes; refused and unrecoverable failed runs return valid report envelopes and retain local JSONL traces. The UI passes recent turns for CVE follow-ups and shows actual returned stage timings after completion.
