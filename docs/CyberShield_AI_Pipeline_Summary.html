1. The big picture

CyberShield AI answers questions such as "What is CVE-2021-44228, is it being exploited, and what should we do?" To answer well it needs two kinds of knowledge: facts about this specific vulnerability and general security knowledge about how attackers behave and how defenders should respond.

Download trusted sources
Clean & convert them
Cut into small passages
Index for fast search
The one decision that shapes everything: NVD and CISA KEV are lookups — we ask them for facts about one CVE. ATT&CK, CWE, OWASP and NIST are the searchable library — we search them for explanations and guidance. Mixing the two would let the system "find" an answer by re-reading data it already looked up, which would make our test scores meaningless.

3. Downloading and cleaning

  • Versioned snapshots, not live fetches. We save a local copy of every source and record its version and a SHA-256 fingerprint. That means anyone can rebuild the exact same knowledge base and get the exact same test results.
  • Resumable downloads. Interrupted downloads and extractions continue from where they stopped instead of starting over — important when 37 large PDFs take a long time.
  • Cleaning per source, not one rule for all. ATT&CK: discard revoked and deprecated techniques. CWE: drop deprecated entries and translate machine markup into readable mitigation bullets. OWASP: keep the cheat sheets, skip templates. NIST: strip repeated page headers, footers and page numbers.
  • Cleaning that does not change meaning. We remove invisible characters and formatting noise, but we never lowercase, stem or shorten text — that would damage identifiers such as CVE-2021-44228 and control names like AC-1.
  • Dedup and minimum size. Repeated documents are rejected by ID and by content fingerprint; records under 100 characters are dropped as unusable.

4. The hard part: PDFs with tables

NIST publications are full of compliance tables — for example, which controls are required for low, moderate and high security baselines. A normal PDF-to-text tool reads the page as a stream of words. The columns disappear, and a row such as AC-1, Policy and Procedures, x, x, x becomes meaningless: nobody can tell which baseline each "x" belongs to.

We switched to pdfplumber, which sees the lines that draw the table grid. Each page is cut into bands: text above a table, the table, text below it. Tables become Markdown, in reading order.

| CONTROL NUMBER | CONTROL NAME | PRIVACY | LOW | MOD | HIGH | | AC-1 | Policy and Procedures | x | x | x | x | | AC-2 | Account Management | | x | x | x |

Every table keeps its header, so a fragment is understandable on its own.

Honest limitation: 6 NIST documents use borderless tables — no drawn lines. Our method cannot see them, so those tables stay as plain text. Figures and diagrams are also skipped, because these PDFs already have a text layer and OCR would be slower and less accurate.

5. Cutting the library into searchable passages (chunking)

A 500-page standard cannot be searched as one block, and a one-sentence fragment is useless on its own. We split documents into passages of about 1,800 characters (≈450 tokens), with a hard cap of 2,600 characters.

  • Tables are never cut mid-row. A table that fits stays whole. An oversized table splits by rows, and every part repeats the header, so no fragment loses its column meaning.
  • Headings travel with the text. Each passage carries the section heading it came from, so a fragment of NIST 800-53 still says which control family it belongs to.
  • Long paragraphs split at sentences, not at arbitrary character positions.
  • Small overlap between prose passages (400 characters) so a sentence cut at a boundary is still findable. Tables are never overlapped — duplicated rows would double-count evidence.
Why not the standard recipe? Most tutorials use a fixed 512-token window or a recursive character splitter. Both cut straight through tables and separate a control from its heading. Semantic chunking (splitting where the meaning changes) costs an embedding pass and still cannot guarantee table integrity. Structure-aware splitting uses information the documents already give us.

6. Making the passages searchable (embeddings + hybrid search)

Two search methods work together:

  • Keyword search (BM25) finds exact terms such as "AC-1" or "Log4j". Fast, but it cannot match different wording.
  • Semantic search (embeddings) converts each passage into a list of 384 numbers — a fingerprint of its meaning. A question becomes the same kind of fingerprint, and we find the closest ones. This finds relevant passages even when the wording differs.

The two ranked lists are merged with Reciprocal Rank Fusion: each passage earns points for how high it appeared in each list. We use ranks instead of raw scores because the two methods score on incompatible scales.

Nothing is embedded on this machine any more — fastembed has left requirements.txt — and there is deliberately no offline fallback, because a local model would embed the query in a different vector space from the stored vectors and silently return junk rankings. Settings are embeddings_base_url, embeddings_api_key, embeddings_model and embeddings_ca_cert in app/config.py (env EMBEDDINGS_BASE_URL, EMBEDDINGS_API_KEY, EMBEDDINGS_MODEL, EMBEDDINGS_CA_CERT), with TLS verified against vm02-ca.crt in the repository root.

What the endpoint forced into the design: at most 16 texts per request, and every input must be under 512 model tokens — the server rejects an over-long input with HTTP 422 naming the token count rather than truncating it quietly. So text is pre-cut to 2,200 characters, which leaves 93.8% of the corpus by character count untouched (a uniform “globally safe” 1,816-character cap would have carried less text than the local index did), and the few dense passages that still overflow are re-cut with the count the server itself reports, bounded to four passes. 429/500/502/503 retry with backoff; an unconfigured endpoint or key raises a clear error. Index build is now about 100 ms per chunk over 10,457 chunks, against the 709-second local build recorded above. Comparability rule: a cosine measured before this change came from the local MiniLM model and is not comparable with one measured after it; the two never share a column or a table. The deterministic source-derived field check stays the only pass/fail authority — the cosine describes similarity, nothing more.

7. How we know it works

We measure two different things and keep them separate:

  • Answer quality: 80 fixed questions whose expected answers were extracted by rule from NVD, KEV and ATT&CK — never written by the model. The model was tested with three prompt styles before retrieval was added. This frozen 80-question set and the Golden-100 workbook were retired on 18 November 2026; CyberShield_Batch10_Consolidated_RAG_Agent_Evaluation_Traceability.xlsx (Batch 10) is now the only evaluation set, so the answer-level numbers in this document are the runs measured on the retired sets.
  • Search quality: 60 questions whose correct document is known and actually contains the answer (15 per source). We measure whether the right document appears in the top 5/10 and how high it ranks.

A test that caught a real problem. Our first retrieval test scored 0.000 for every method. That was not a search failure: the questions asked "which ATT&CK technique maps to CVE-X", but the CVE number does not appear anywhere in the technique document — that link only exists in a database. No text search can answer it. We replaced that test with the 60-question benchmark above rather than report a misleading score.

Scores on the strict one-document labels understate ATT&CK and CWE performance: the correct answer is sometimes a sub-technique or a different source with the same content, which our labels count as a miss.

The 60-query benchmark measures the frozen generic index only. The NVD reference store added on 16 November 2026 sits beside it — searched first for the investigated CVE, with the generic index left untouched — so these scores stay comparable across versions.

8. Choices we deliberately did not make

Tempting optionWhy we did not take it
Query every source live at question timeAnswers would change as sources change, tests would not be reproducible, and it would blow the 20-second response budget.
Flatten PDFs to plain text (pypdf)Destroys table columns, and NIST baselines are the most valuable content in those PDFs.
Fixed-size token windowsCuts tables and separates controls from their headings.
A separate vector search service (Elasticsearch, Qdrant, a hosted vector database)A whole index fits in 16 MB and searches in 8 ms; a service would add operations burden with no benefit, and it would mean a network hop for data that must not leave this machine. Partly revised 18 November (D29): we did adopt FAISS, but as an in-process library over a local flat index file — exact search, the same 8 ms, and the same tie rule the frozen benchmarks were measured under, so no recorded number moved. Still true after D32: the index itself never leaves this machine. The course embedding endpoint receives text to vectorise and stores nothing; a hosted vector database would have kept the corpus somewhere else.
Let the model invent CVE→ATT&CK mappingsNo official mapping exists, so we ship only curated verified mappings and report the rest as unknown.
Model-as-judge gradingThe model would grade its own work. All grading is rule-based against frozen facts.

9. Known gaps

  • English-only corpus, weighted toward US security guidance; ATT&CK Mobile and ICS are not included.
  • Borderless NIST tables and figures are not recovered as structured content.
  • For this demo, any dated KEV snapshot at or before investigation time is accepted; undated or future-dated snapshots remain unknown. Production freshness requirements need separate review.
  • Vectors now come from the course embedding endpoint rather than a local model (18 November 2026, D32): a fresh checkout cannot rebuild the index offline, so an endpoint outage blocks a rebuild, and the served model weights cannot be inspected. The earlier local MiniLM choice was made for speed on this CPU, not because it is the best embedding model available.
  • Retrieval labels are strict, so ATT&CK/CWE scores are a conservative lower bound.
  • NVD reference pages are local snapshot copies fetched on 16 November 2026; they may have changed since, and 22 of the 56 referenced CVEs have no usable reference chunks (unfetched or too-short pages) and simply use the generic corpus.

10. The 60-second version

"We use six trusted security sources: NVD tells us about the vulnerability, CISA tells us whether it is being exploited, ATT&CK describes attacker behaviour, CWE explains the weakness, OWASP gives practical fixes, and NIST gives formal controls — and since 16 November we also snapshot the pages each NVD record itself cites and search them first for the investigated CVE. We download versioned snapshots instead of querying live, clean each source according to its own structure, and preserve what matters — IDs, headings and especially NIST's compliance tables, which we recovered as real tables instead of broken text. We cut the library into 10,457 passages that keep tables and headings intact, and search them with both keywords and semantic fingerprints, which beats either method alone. Every claim in a response has to cite a passage we actually retrieved, and every design choice above is backed by a measurement rather than a guess."
