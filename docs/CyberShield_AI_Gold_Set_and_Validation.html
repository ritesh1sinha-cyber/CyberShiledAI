How the gold dataset was built, checked and used

The gold dataset is our exam, answer key and marking scheme. This guide explains where each expected answer comes from, what the audit corrected, and how a real answer is marked pass or fail.

Retired on 2026-11-18; the method still stands. This page documents the 80-question frozen set, which is no longer the evaluation set. Batch 10 (CyberShield_Batch10_Consolidated_RAG_Agent_Evaluation_Traceability.xlsx, 110 gold claims over 10 investigations) is, and data/evaluation/README.md is its index. The files this page names — baseline_scores.json, review.csv, architecture_*_20261116.json, answer_metrics_benchmark_20261116.json — are no longer in this tree, and every cosine here was produced by the local MiniLM model that decision D32 removed. What did not change: no language model writes an answer key or decides pass or fail.

1. What “gold” means here

A model answer is not considered correct just because it sounds confident. It must agree with trusted evidence. For each test question, we therefore store the question, the facts we expect, the sources that support them, and deterministic rules for marking an answer.

80final-answer evaluation questions
40unique target CVE identifiers
810audit checks passed after correction
0remaining audit failures
No language model writes the answer key or judges the result. Fixed Python rules extract the facts and grade the answers. This makes repeated experiments comparable.

Do not confuse two different exams: these 80 questions evaluate the final answer. A separate 60-query retrieval benchmark checks whether BM25, dense search or hybrid search finds the right documents. A good final answer needs both retrieval quality and correct use of structured NVD/KEV tools.

2. The construction process

Save trusted snapshots
Select a varied CVE pool
Extract facts by fixed rules
Audit answers and sources
Freeze the exact file
  1. Choose the evidence first. NVD supplies CVE dates, affected configurations, CVSS and weakness references. CISA KEV supplies exploitation status and required action. The ATT&CK STIX bundle supplies direct technique-description CVE mentions. CWE supplies weakness names and mitigation guidance.
  2. Select the CVE pool. The builder combines curated important CVEs, recent KEV entries with vendor/year diversity limits, and non-KEV NVD keyword results. Duplicate CVEs are removed. Some CVEs intentionally appear in more than one question category because a factual question and a remediation question test different skills.
  3. Apply category templates. Templates create factual, CVSS, KEV, ATT&CK, remediation, multi-step and adversarial questions. This gives repeatable coverage rather than 80 improvised prompts.
  4. Derive—not invent—the expected answer. Every expected fact comes from a saved source response. The reference answer is assembled from those same facts.
  5. Audit and freeze. The audit re-reads the raw NVD, KEV, ATT&CK and CWE snapshots, checks the answer key against its own grader, and records a SHA-256 hash. The freeze script refuses a stale or failed audit.

Implementation: scripts/build_gold.py, scripts/audit_gold.py, scripts/freeze_gold.py and app/grading.py.

4. The fact-selection rules

FactDeterministic ruleWhy this matters
CVSSChoose cvssMetricV31, then V3.0, then V2. Prefer the Primary entry within the selected set. Never combine fields from different metric sets. If severity is absent, derive it from the selected version's score bands.Prevents a score from one authority being paired accidentally with a vector or severity from another.
ProductPrefer the KEV vendor/product name when the CVE is listed; otherwise use vulnerable NVD CPE configurations. Declare CISA KEV as a required source when its product label is used.Keeps familiar product names while preserving truthful source attribution.
KEV statusCompare the CVE with the successfully loaded catalog snapshot and record its catalog version. “Not listed” is time-bounded, not a claim that exploitation never occurs.Separates evidence of known exploitation from absence in one catalog snapshot.
KEV actionCopy the complete requiredAction text; do not shorten it with an ellipsis.A question asking “what action is required?” must actually grade the action.
CWEPrefer an NVD-assigned weakness, then another NVD-source assignment. Within that order, choose the first entry present in the CWE snapshot with mitigation text; fall back to the first present entry.Avoids arbitrary first-list selection and avoids deprecated entries with no usable guidance.
MitigationInclude the first complete CWE phase and description. Add the full KEV action when available.The reference remains readable without cutting off the security advice.
ATT&CKAccept a mapping only when the Enterprise technique description directly mentions the CVE. Include every verified technique found for that CVE.A plausible technique is not sufficient evidence. No official general CVE→technique mapping is assumed.
Unknown CVESave NVD's actual empty response for CVE-2099-99999 (totalResults: 0) and hash it in provenance.Absence is verified through a real lookup, not inferred from a missing local file.

5. What each gold record contains

FieldPurpose during validation
test_id, category, queryIdentifies the exam question and its reporting bucket.
expected_factsThe source-derived values that the answer must contain. These are facts, not a requirement to copy the whole reference wording.
required_sourcesDeclares which evidence sources are needed to support the expected answer.
must_includeRequired identifiers or values. The grader now enforces these for every category.
must_not_claimA forbidden affirmative claim. It is used narrowly—for example, the false Log4j score premise—so a valid correction is not mistaken for a violation.
grading, answerabilitySelects exact, rubric or behavioural marking and distinguishes answerable, unanswerable and refusal cases.
reference_answerA complete example answer used for review and self-grading. The model does not have to repeat it word for word unless an exact fact requires it.
provenanceSource URL, raw NVD response hash, KEV catalog, ATT&CK snapshot and generation time. Remediation rows also record CWE source information.

6. What the double-check found and corrected

The first audit found no mismatches in the stored source facts: publication dates, CVSS values, KEV status/dates, ATT&CK mappings and CWE identifiers agreed with the snapshots. The important defects were in coverage, completeness and grading.

7. Worked validation example: CS-022

Question: “Report the CVSS version, base score and severity for CVE-2017-7921.”

Expected facts from the cached NVD response:

{
  "cvss_version": "3.1",
  "cvss_score": 9.8,
  "severity": "CRITICAL"
}

Example A — correct answer

{"cvss": {"version": "3.1", "score": 9.8, "severity": "CRITICAL"}}

The grader parses the JSON, flattens the nested cvss fields, and compares each value.

CheckResult
CVSS version = 3.1Pass
CVSS score = 9.8Pass
Severity = CRITICALPass
Required text includes 9.8 and CRITICALPass
Overallpassed = true; score = 1.0

Example B — plausible but wrong answer

{"cvss": {"version": "3.1", "score": 9.8, "severity": "HIGH"}}
CheckResult
CVSS version and scorePass
Severity = CRITICALFail—the answer says HIGH
Required text includes CRITICALFail
Overallpassed = false; fact score = 2/3
A partial score does not mean the question passed. Exact questions pass only when every expected fact and every required/forbidden-text constraint passes. The partial score is diagnostic; the pass flag is the headline result.

How this becomes an experiment result

  1. scripts/baseline_raw.py asks the raw model each question and saves the answer trace. It does not retrieve evidence.
  2. app/grading.py runs grade_record(record, answer) for each saved answer.
  3. scripts/grade_baseline.py aggregates pass rate, partial score, JSON validity, latency and category results into data/evaluation/baseline_scores.json.
  4. The later RAG configuration is graded with the same gold file and function. Comparing those results with R0 isolates the improvement from tools and retrieval instead of changing the exam.

The cached raw-model traces were regraded after this audit without new model calls. Corrected overall pass rates are P0 14%, P1 5% and P2 11%; these are raw-model baselines, not RAG scores.

8. Commands for repeatable validation

Run these from the project folder in cmd.exe:

.venv\Scripts\python.exe -m scripts.audit_gold
.venv\Scripts\python.exe -m pytest tests\test_gold.py tests\test_grading.py -q
.venv\Scripts\python.exe -m scripts.grade_baseline

When intentionally changing the gold set:

.venv\Scripts\python.exe -m scripts.build_gold
.venv\Scripts\python.exe -m scripts.audit_gold

Then inspect data/evaluation/review.csv, mark each row approved or rejected with an honest review note, and run:

.venv\Scripts\python.exe -m scripts.freeze_gold
.venv\Scripts\python.exe -m scripts.grade_baseline

The freeze command refuses pending rows, a changed gold file, or a missing/stale/failed audit. Rebuilding changes the gold hash, so previous experiment scores must be regenerated rather than silently compared with the new exam.

9. Limits we still need to state

  • Snapshot-bound truth: NVD and KEV can change. The answer key is correct for the recorded snapshots, not forever.
  • Product is not version matching: the gold product label does not prove that every installed version is affected.
  • ATT&CK scope is narrow: a direct description mention is verified evidence, not proof that every attack using that CVE follows that technique. No mention means “no verified mapping in this snapshot,” not “no relationship exists.”
  • CWE guidance is general: vendor instructions and KEV action remain necessary for a specific vulnerability.
  • Rule grading can be conservative: a valid paraphrase may fail an exact required-action check, while a fluent wrong answer can pass a simple keyword rubric only if all required conditions are present. Category-level failures should be sampled manually when interpreting results.
  • Review independence: this correction was an AI source audit requested by the user, not an independent human security review. The manifest records independent_human_review: false.

10. The short explanation for a presentation

“Our gold set is a fixed exam with a source-backed answer key. We did not ask a model to invent the questions' answers or to grade itself. Python rules extracted dates, CVSS metrics, KEV actions, CWE guidance and direct ATT&CK references from saved authoritative snapshots. Our second audit found that the original facts were right but some questions were not fully graded and some example answers were incomplete. We corrected those gaps, independently re-read the raw sources, and passed 810 checks across all 80 records. Every reference answer now passes the same grader used on the model. A model answer passes only when all required checks pass, and every experiment is tied to the frozen dataset hash so we compare systems on exactly the same exam.”
