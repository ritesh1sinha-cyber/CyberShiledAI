1. Where we are now

Current architecture: Streamlit passes the current question and recent turns to FastAPI over one streamed request. A deterministic safety gate runs first, then Evidence with Qwen interprets the CVE or follow-up, searches the CVE’s own NVD reference pages first, and queries and reviews RAG across up to three rounds. Analyst drafts; the Critic reviews and can send the draft back for one revision; deterministic validation assembles the report. The UI shows each agent’s progress as it happens and, beside every citation, the paragraph that retrieval actually used. Local JSONL history retains each request trace and can be read back per investigation.

33Dense vectors moved into a FAISS index, with the old ranking rule kept (D29) DoneThe dense retrieval layer had been a NumPy matrix: every query multiplied the whole 10,457 × 384 array in memory. It now searches a faiss.IndexFlatIP file, which is still exact search — no approximate index and no quantisation, so no retrieval quality was traded away. Before switching, the ranking risk was measured rather than assumed: raw FAISS reordered 4 of 140 frozen benchmark queries and 59 of 2,000 stress queries at k=50 and changed top-50 membership on some of them, because a heap pop order and SIMD accumulation are not numpy's BLAS. That mattered because the corpus contains 32 exact duplicate rows (largest duplicate group 19), so ties at the cut are real. The fix is in app/vector_store.py: ask FAISS for k + 32 candidates, read those vectors back, rescore them in float64, and sort by (score descending, row ascending) — the rule every frozen number was measured with. Measured afterwards: 0 ranking mismatches on the same 140 and 2,000 queries, and the 60-query benchmark reproduced every score field of the 2026-11-06 artifact exactly (hybrid recall@5 0.817, recall@10 0.833, MRR 0.596, nDCG@10 0.655, per category included). Nothing was re-embedded: the FAISS file was derived from the shipped embeddings.npy, so the chunk hash and all three earlier index hashes are unchanged, and the new file is recorded in the manifest. No speedup is claimed — dense latency was already ~8 ms and measured 8.1 ms. 304 tests pass (13 new). scripts/verify_faiss_parity.py is the standing guard and exits non-zero if the production path ever disagrees with the recorded rule. 3. Why the Planner was removed

The earlier Planner classified intent and packaged the CVE and retrieval options into a plan. Mentor review identified that the runtime did not need a separate planning action: the next Evidence step performed retrieval using that same information. The extra model call and schema added latency and another failure point without a measurable planning benefit.

The current flow keeps deterministic request validation and safety refusal in code. Evidence with Qwen handles CVE/follow-up interpretation and RAG query/relevance work. The model cannot override a CVE explicitly supplied in the current question, and it does not own safety policy.

5. Exactly how Evidence works for one CVE

This section follows one question from start to finish. The most important point is simple: NVD and KEV are exact local lookups; CWE, OWASP, NIST and ATT&CK passages are retrieved from the chunked library.

Example user input: “Investigate CVE-2021-44228: severity, KEV status and remediation.”

Step A — Evidence with Qwen interprets the question

The deterministic gate checks unsafe intent first. Evidence with Qwen then copies the explicit CVE or resolves a follow-up from recent user context, labels the intent and formulates a concise retrieval query. The model does not supply vulnerability facts.

Step B — Python reads the stored NVD record

The Evidence Agent checks for this local file:

data/raw/nvd/CVE-2021-44228.json

It reads named fields such as description, publication date, CVSS metrics, vulnerable configurations and CWE weaknesses. For this CVE, deterministic rules select CVSS 3.1, 10.0, CRITICAL. There is no chunk search here: it is like opening a structured form and reading its fields.

Is NVD called live? Not in the current Evidence Agent. The file was fetched from the NVD API and cached locally earlier in the build (the downloader script that filled this cache was retired on 2026-11-18, and the cached records themselves remain); Evidence only reads the cache. If a user enters a CVE with no cached file, the current node returns cve: null and records a limitation. It does not claim that the CVE is nonexistent and does not silently call the live API.

Step C — Python checks the stored KEV catalogue

The agent finds the exact CVE ID in data/processed/kev.jsonl. For Log4Shell it returns known_exploited, Apache Log4j2, the KEV dates and required action. KEV is not chunked. For this demo, any dated snapshot at or before investigation time is accepted; undated or future-dated snapshots remain unknown.

Step D — Evidence with Qwen and code build a focused search query

The NVD record lists several CWE weaknesses. A deterministic selection rule prefers the NVD-assigned weakness with mitigation guidance. For Log4Shell this selects CWE-917. Evidence with Qwen interprets the user intent; code appends the selected CWE and remediation terms to focus retrieval:

Investigate CVE-2021-44228: severity, KEV status and remediation
CWE-917
Improper Neutralization of Special Elements used in an Expression Language Statement
remediation mitigation security controls

This is why the first result is the relevant CWE-917 guidance instead of an unrelated passage that merely mentions logging.

The Evidence Agent calls Retriever.search() in app/retrieval.py. This is ordinary local Python code, not another Qwen request; the one network call the dense half makes is the single embedding request that turns the question into a vector (D32), and a BM25-only search makes none.

  • Reference-first (16 November 2026): before the generic search, the agent ranks the investigated CVE’s own fetched NVD reference chunks (data/processed/reference_chunks.jsonl) with a per-CVE BM25 scorer and places those NVD_REF citations ahead of generic results.
  • BM25 keyword search finds exact terms such as CWE-917.
  • Dense embedding search finds passages with similar meaning even when the wording differs. Since 18 November 2026 (D32) the vector a query becomes comes from the course embedding endpoint through app/embeddings.py, the same client that produced the stored vectors; before that day a local MiniLM model produced both.
  • Reciprocal Rank Fusion merges the two ranked lists. It is simply a rule that rewards passages ranking highly in either or both lists.
  • The agent takes the top eight results from data/processed/chunks.jsonl.

Step F — passages receive IDs and citations

For every selected chunk, Python records its text, title, chunk ID and source URL. It assigns an ID such as EV-0005, creates exactly one matching citation, and labels the passage retrieved rather than verified. If source metadata is missing, the chunk is skipped.

A high search rank is not treated as proof of truth. It means “this passage appears relevant and here is its source.” The Analyst must cite these passages as retrieved context; the Critic reviews semantic use and the Final Validator enforces the final report boundary.

6. What the Analyst does

The Analyst is the writer, not a new source of knowledge. It receives the exact EvidencePackage from the previous node and must turn it into eight short sections. It cannot search the web, call NVD, choose a risk tier, or add a fact from model memory.

Input: verified NVD/KEV facts + verified ATT&CK mappings + retrieved CWE/OWASP/NIST/ATT&CK passages + limitations. Output: strict JSON containing eight text sections and the evidence IDs used by each section.
When a draft is rejected (16 November 2026): a draft that fails deterministic validation, or that the Critic rejects, is revised once instead of being discarded. The revision request carries the previous draft, the Critic’s issues, the full evidence package and the exact validation failure. The system prompt forbids placeholder evidence IDs such as EV-0000: the limitations section must use an empty evidence_ids list.

What Python checks before accepting the draft

  • Exact shape: all eight sections must exist. Extra fields, missing fields, malformed JSON and truncated output are rejected.
  • Real citations: every EV-0001-style ID must exist in this request’s EvidencePackage. A made-up ID such as EV-9999 fails.
  • Suitable source type: for example, affected products must cite product evidence, KEV must cite KEV evidence, and risk may use only CVSS/KEV drivers.
  • Unknowns stay unknown: missing NVD facts, missing products, unknown KEV status and missing verified ATT&CK mappings cannot be replaced with invented text.
  • Important values cannot drift: code rejects unrelated CVE IDs, unverified ATT&CK technique IDs and unsupported CVSS numbers.
  • KEV action has KEV support: when CISA supplies a required action, the remediation section must cite that KEV evidence as well as any retrieved guidance used.
  • No model-owned risk tier: the output schema has no risk-tier field, and code rejects statements such as “Risk tier: critical.” The Final Validator calculates the tier after the Critic finishes.
What this does not prove: a valid citation proves that a source exists and belongs to the right section; it does not prove that every sentence perfectly represents that source. The Critic checks semantic support, while deterministic code adds known citation findings.

Real failures that improved the implementation

  1. The first drafts copied the long NVD description and used all 400 output tokens before finishing the JSON. The system rejected them. Clear section boundaries and short paraphrase instructions produced a complete 332-token draft without increasing the cap.
  2. A later draft used CISA’s “apply updates or remove assets” action but cited only CWE. The new KEV-citation rule rejected it. We also added the required-action text to the KEV evidence record so the citation now points to the actual supporting claim.
  3. The accepted draft’s summary says “Critical” but cites only the NVD description, EV-0001. The Critic records that EV-0002 is required, and the Final Validator marks the report partial with a visible limitation rather than hiding or silently repairing the problem.

7. What the Critic does

The Critic is a reviewer, not a second writer. It receives the same EvidencePackage and the AnalystDraft, checks all eight sections in order, and returns at most three findings. There is no corrected-draft, replacement-text, risk-tier or final-report-status field.

One revision path (16 November 2026): when the first review reports a failing status — or the draft itself failed deterministic validation — the workflow routes back to the Analyst once with the review issues, and the Critic re-reviews the revised draft. The Critic still never rewrites the draft; the Analyst rewrites and the cap is one revision per investigation.
Qwen reviews meaningSupport, completeness and uncertainty. It can identify a specific unsupported or incomplete statement, but cannot add facts.
Python checks traceabilityCitation presence, allowed claim types and summary CVSS/KEV citation gaps are deterministic. The four pass/fail values are derived from the final findings.
  • Every evidence ID, CVE ID and ATT&CK technique in a model finding is validated before any contradictory finding is removed.
  • Model-owned citation findings are replaced by deterministic citation checks. This prevents repeated false claims that an already-cited ID is missing.
  • An uncertainty finding against a correctly null section is removed: null is how unavailable facts are preserved, not a defect.
  • The predictable plural model alias citations is normalized to the strict issue category citation. Other invalid sections or schema shapes are rejected.

8. What the Final Validator does

The Final Validator is ordinary Python code, not a fourth Qwen call. It is the last authority before a report leaves the investigation workflow.

  1. Recheck the hand-off: the EvidencePackage, AnalystDraft and CriticReview must still satisfy their contracts. Invalid references, changed facts or model-selected risk are rejected.
  2. Calculate risk: critical means KEV-listed with CVSS at least 9.0; high means KEV-listed or CVSS at least 9.0; medium means CVSS at least 7.0; low means a lower present score. With no CVSS and no higher-tier KEV condition, risk is unknown.
  3. Keep claim-level citations: the final report now stores summary_evidence_ids and risk evidence_ids, in addition to remediation IDs and the global source list. Every reference must resolve to this request’s evidence.
  4. Assign an honest status: completed requires no Critic findings and no missing core facts. Otherwise the report is partial, with the finding or missing fact shown in limitations. The API service creates separate refused and failed reports when the workflow stops before final validation.

14. Small glossary

AgentA named job in the workflow. Evidence with Qwen interprets/retrieves, Analyst writes and Critic optionally reviews. They run one after another, not at the same time.
NodeOne executable step in LangGraph. The graph runs Evidence, Analyst, optional Critic and Final Validator; the deterministic safety gate runs before the graph.
Evidence packageA structured bundle of facts, passages, source links, limitations and timing passed from Evidence to Analyst and Critic.
DraftThe Analyst’s eight-section answer. The Critic reviews it, then the Final Validator uses it to assemble the final Report.
ReviewThe Critic’s findings across support, completeness, citations and uncertainty. It does not replace the draft or assign final status.
Final ValidatorDeterministic code that calculates risk, checks report citations and assigns completed or partial status for an investigated request.
CitationA pointer from an evidence ID to its real source URL. It shows where a claim came from; it does not by itself prove that the wording is correct.
NullA structured “not available” value. The draft uses it instead of inventing a fact or using zero, “N/A” or a guessed answer.
Qwen callOne sequential request to the course-hosted model. A typical investigation uses three; with three retrieval rounds and one Critic-driven revision the worst case is ten (one interpretation + up to three retrieval reviews + analyst + critic, retried once if the review is unusable + revision analyst + critic re-review, retried once).
Embedding requestOne call to the course embedding endpoint that turns text into a 384-dimensional vector for bge-small-en-v1.5. It is not a Qwen call — it writes no prose — and since 18 November 2026 (D32) it is the only way any vector in this project is made: one per dense search, plus the batches scripts/build_index.py sends when the index is built, plus the calls the descriptive cosines need during evaluation. A BM25-only search makes none.
FastAPIThe local web-service boundary. It validates input and exposes investigation, health and history endpoints without giving the browser direct access to Qwen.
StreamlitThe local browser interface for entering a question and reading the report, sources, timings and history.
JSONL traceA local text file with one JSON record per investigation. Each record links the request, evidence, model usage, response, timings and any safe error metadata.
Langfuse traceA local mirror of one investigation in the self-hosted Langfuse v2 bound to 127.0.0.1:3100: one trace, one span per graph node, and one generation per Qwen call carrying its raw prompts and raw completion. Off unless explicitly enabled with both keys set and a loopback host, and never the system of record — the JSONL trace above still is.
P50The median measured time: half of observations are faster and half are slower. It describes a typical run, not the worst case.
P95The time at or below which 95% of measured observations fall. This project uses the nearest-rank method and always states the observation count and population.
Response contractThe required response shape and allowed values. A valid contract means the API response is well formed; it does not mean the answer passed the gold question.
Deterministic gradingFixed code checks exact facts, required remediation elements or expected behavior. Qwen does not decide whether its own answer passes.
NVD_REF citationA citation to a passage from the fetched pages the NVD record itself cites. It is marked retrieved like any ranked passage, and is searched before the generic corpus.
RevisionOne bounded re-prompt of the Analyst with the previous draft, the Critic’s issues and the exact validation failure. The Critic re-reviews the result; the cap is one revision per investigation.

D17 — up to three retrieval rounds

app/evidence.py now sets MAX_RAG_CALLS = 3: the initial query plus at most two reviewer-driven refinements. Repeats of an already-used refined query are skipped, and a run that exhausts all three rounds while the reviewer still judges the passages insufficient records the limitation “Retrieval review still judged the passages insufficient after 3 search rounds.” Each extra round adds one search plus one review call, so worst-case latency grows.

D18 — the Critic can send the draft back once

app/workflow.py gained a conditional edge from Critic back to Analyst, capped at ONE revision per investigation. The re-prompt is the CRITIC_REVISION_REQUEST built by build_revision_prompt in app/analyst.py. Two failure paths are defined: a revision that fails deterministic validation uses the existing deterministic fallback, and an unparseable second review reverts to the original draft plus the first review, recording the revision_review_failed trace flag instead of failing the investigation.

D19 — a bad first draft is reviewed and revised before fallback

A first Analyst draft that parses but breaks a deterministic content rule is no longer replaced instantly. The parsed draft is kept with the draft_invalid flag, the Critic reviews it, and the workflow forces one revision even when the Critic passes — the validation error is handed to the Analyst as the issue to fix. Deterministic assembly now happens only for unparseable or truncated output, or when the revision still fails validation. When the pre-revision draft was itself invalid and the post-revision review errors, the revert path builds the deterministic draft instead of shipping a draft that final validation would reject. app/history.py records first_draft_invalid, first_draft_invalid_reason, draft_invalid_reason and draft_fallback_reason so fallback-after-revision stays visible.

D29 — the dense layer moved to FAISS without moving a single frozen number

  • What was asked: “use faiss database for vector instead of numpy”. Read plainly, the dense retrieval layer should stop being a raw array multiplied in memory and become a proper vector index.
  • Why this was risky, in one sentence: all our recorded retrieval results were produced by one very specific ordering rule — highest cosine first, and when two passages score exactly the same, the one stored in the lower row wins — and FAISS does not promise that rule, because it answers from a heap and adds up dot products in a different order inside its SIMD kernels.
  • Measured before touching anything: scripts/verify_faiss_parity.py compared raw FAISS answers with the old NumPy rule and found the order differing on 4 of 140 real benchmark queries and 59 of 2,000 stress queries at k=50, plus one query where the actual set of top-50 passages changed. The reason it is not a corner case: the index holds 10,457 rows but only 10,425 distinct vectors, so 32 rows are exact duplicates of another row and the biggest such group is 19 — tied scores at the cut happen.
  • Exact change: app/vector_store.py owns the vectors now. write_index() refuses unnormalised input (inner product equals cosine only for unit-length vectors) and writes one FAISS file; VectorStore.search() asks for k + 32 candidates — the margin is larger than the biggest duplicate group on purpose — reads those vectors back with reconstruct_batch, recomputes the scores in double precision, and applies the shipped tie rule itself. app/retrieval.py loads embeddings.faiss instead of a .npy matrix. BM25, the fusion step and the reference-first retriever were not touched, and no embedding model was re-run: scripts/build_index.py --from-npy derived the FAISS file from the vectors we already had. (That lasted one day: D32 below rebuilt every vector in that file through the hosted endpoint.)
  • Provenance proof: comparing the index manifest before and after the change, the source chunk hash and the hashes of bm25_tokens.jsonl, embeddings.npy and ids.json are byte-identical; the manifest only gained dense_backend and the hash of the new 16 MB index file.
  • Verification: the parity run reported 0 mismatches through the production path at both k=8 and k=50, which is what allowed the switch to be called a format change rather than a behaviour change. The measurement script that proved it is no longer in the tree; the same ordering rule is now held by tests/test_vector_store.py, which fails if the store stops matching it. Re-running the frozen 60-query benchmark through FAISS reproduced every recorded score field, including the per-category split; the 2026-11-06 artifacts were left untouched and the FAISS reproduction archived alongside them as retrieval_scores_benchmark_faiss_20261117.json. 304 offline tests pass (10 new in tests/test_vector_store.py, including a planted group of 50 duplicate rows that must still rank like numpy does, and 3 new wiring tests in tests/test_retrieval.py).
  • Honest accounting of the benefit: no speedup was found or claimed — at 10,457 vectors the old path already answered in about 8 milliseconds and the new one measured 8.1. What you actually get is a standard index file format, one clear owner for the vector bytes instead of a matrix floating in each process, and a clean swap point if the corpus later grows enough that exact search stops being affordable.
  • Where this still could bite: the 32-candidate margin is a fixed number, so a query with more than 32 equal scores straddling the cut could still be ordered differently; the parity check of that step sampled rather than proved (2,000 stress vectors, 140 distinct frozen query strings), and it read embeddings.npy as its comparison seed, so deleting that file would leave only the unit tests guarding the rule. The vectors are stored twice on disk (~32 MB) for exactly that reason. The vectors themselves stay on this machine: the index is a file in the gitignored data/index/ directory. What changed after this step (D32) is how those bytes were made and how a query is turned into a vector — a dense search now makes exactly one request to the course embedding endpoint, and a BM25-only search still makes none.

D32 — the local embedding model was replaced by the course embedding endpoint

  • What changed: every vector in the system used to be made on this machine by a local all-MiniLM-L6-v2 model behind fastembed. Now app/embeddings.py holds one client for the course embedding endpoint, and it is the only producer of vectors anywhere: the index build, the vector a query becomes during retrieval, and the descriptive answer-versus-reference cosine in app/answer_layers.py all go through it. One endpoint and one model for all three jobs is the point — bge-small-en-v1.5, 384 dimensions, returned already L2-normalised, so an index and a query can never be built in different spaces.
  • Why the earlier choice was not a mistake: the local model was picked on 11–12 November because it needed no credentials, measured about 14.7 texts per second here, and kept every embedding on this machine. Those reasons were correct then. They were superseded, not disproved, when the course endpoint became the required path; the recorded numbers from that period stay as measured and are labelled as local-model measurements wherever they appear.
  • Configuration, with nothing secret written down: four settings in app/config.py — embeddings_base_url, embeddings_api_key, embeddings_model, embeddings_ca_cert — come from EMBEDDINGS_BASE_URL, EMBEDDINGS_API_KEY, EMBEDDINGS_MODEL and EMBEDDINGS_CA_CERT in .env. TLS is verified against the repository’s own vm02-ca.crt. The endpoint host and the key appear in no document, no test and no trace: only the environment-variable names are ever quoted.
  • What the endpoint’s own limits forced into the design: sixteen texts at most per request, and every single input under 512 model tokens. Over-length is refused, not silently truncated: the server answers HTTP 422 naming the token count it hit. So the client pre-cuts to 2,200 characters, which leaves 93.8% of the 10,457 chunks completely untouched, then re-cuts only the inputs the server rejected using the count the server reported, bounded to four passes. A 429, 500, 502 or 503 is retried with backoff; an unset endpoint or key fails immediately with a message that says what to set.
  • Deliberately no offline fallback: falling back to a local model would embed queries in a different vector space from the stored ones, which is worse than not answering. A missing configuration is therefore a visible error, never a silent substitution.
  • Cost and commands: scripts/build_index.py lost --model on purpose (choosing another model there would build an index nothing here can search) and kept --from-npy, which re-derives embeddings.faiss from the matrix already on disk without calling the endpoint. Index building is now a network-bound job at roughly 100 ms per chunk, against the 709 s the earlier local build recorded for the whole corpus. fastembed is out of requirements.txt.
  • The rule that now governs every cosine in this document: a cosine measured before 2026-11-18 came from the local MiniLM model and a cosine measured from that day came from the hosted endpoint; they are different measurements, are never mixed in one column or one table, and any figure quoted here states which one produced it.
  • What did not move: the deterministic source-derived field check is still the only pass/fail authority. Moving the embeddings changed a measurement tool, not the verdict rule, and the cosine stays a descriptive number beside that verdict.
  • Verification: tests/test_embeddings.py adds thirteen checks against an httpx.MockTransport fake, so they need no credentials and open no socket; tests/test_retrieval.py injects a FakeEmbedder, and one of its cases proves a BM25-only search never reaches the endpoint at all. The suite is 338 tests across 25 files and every one of them runs offline.
  • Where this still could bite: a query and an index build now depend on a network service, so an outage or a certificate change is a visible failure rather than a degraded answer, and each of the four re-cut passes spends a request finding the server’s real token limit on an unusually long chunk. The 2,200-character pre-cut is a character budget standing in for a token count, so the small share of chunks longer than it are cut shorter than the model could read.
